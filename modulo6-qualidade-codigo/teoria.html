Teoria

🧭 Objetivo desta etapaDistinguir código que apenas funciona de código que pode ser entendido, testado, depurado e alterado com segurança.
Estratégia: leia uma seção por vez, execute mentalmente os exemplos e anote uma dúvida ou exemplo próprio antes de avançar para a prática.

1. O que é qualidade de código

Um software passa a maior parte da vida sendo lido e modificado, e não escrito. Código de qualidade facilita esse trabalho. Atributos principais:

AtributoPergunta que responde
CorreçãoFaz o que os requisitos pedem?
LegibilidadeOutra pessoa entende rápido?
ManutenibilidadeÉ fácil corrigir ou ampliar?
TestabilidadeDá para verificar automaticamente?
DesempenhoUsa tempo e memória de forma adequada?
SegurançaResiste a uso indevido e entradas inválidas?

Regras de formatação

  • Uma instrução por linha; indentação de 4 espaços; chaves { } sempre, mesmo em if de uma linha.
  • Métodos curtos que fazem uma coisa só (princípio da responsabilidade única).
  • Evitar números e textos “mágicos”: use const com nome.
  • Formatar o arquivo no Visual Studio: Ctrl+K, Ctrl+D. Para toda a equipe seguir o mesmo padrão, crie um arquivo .editorconfig (Projeto → Adicionar → Novo Item → Arquivo editorconfig).

3. Documentação de código

Comentário comum (//)

Explica o porquê de uma decisão, não o óbvio. Compare:

RuimBom
i++; // soma 1 em i// Limite de 500 definido pela regra RF04
Blocos de código antigo comentados “para o caso de precisar”Remover (o Git guarda o histórico)

Comentário XML (///)

Digite /// acima de uma classe ou método e o Visual Studio gera o modelo. O texto aparece no IntelliSense para quem usar seu código.

TagUso
<summary>O que a classe ou método faz (obrigatória)
<param name="x">Descreve um parâmetro
<returns>Descreve o valor devolvido
<exception cref="T">Quando uma exceção é lançada
<remarks>Observações adicionais, regras de negócio
<example>Exemplo de uso

Para gerar o arquivo de documentação: propriedades do projeto → Build → Saída → Arquivo de documentação XML (ou <GenerateDocumentationFile>true</GenerateDocumentationFile> no .csproj).

4. Reutilização de código e refatoração

DRY (Don't Repeat Yourself): cada regra deve existir em um só lugar. Refatorar é melhorar a estrutura do código sem mudar seu comportamento, e os testes garantem que nada quebrou.

Sinal de problema (“code smell”)SoluçãoAtalho no Visual Studio
Trecho repetido em vários lugaresExtrair métodoSelecionar → Ctrl+R, M
Nome que não explicaRenomear (atualiza todas as referências)F2 ou Ctrl+R, R
Número ou texto fixo repetidoIntroduzir constanteCtrl+. (Ações Rápidas)
Método muito longoDividir em métodos menoresCtrl+R, M
Classe fazendo coisas demaisExtrair classeCtrl+.
Muitos if por tipoHerança/polimorfismo ou enum + métodoManual
💡 Regra de ouro da refatoração: mudar pouco, rodar os testes, repetir. Se os testes quebrarem, você sabe exatamente qual mudança causou.

5. Otimização de código

Otimizar é fazer o programa gastar menos tempo ou memória. A regra é: meça antes, otimize depois. “A otimização prematura é a raiz de todo o mal” (Donald Knuth): código claro e correto vem primeiro.

TécnicaQuando usar
Escolher a estrutura certaList para ordem; Dictionary para buscar por chave; HashSet para verificar pertencimento
StringBuilderMontar textos grandes em laço (concatenar com + cria uma nova string a cada volta)
Tirar trabalho de dentro do laçoCálculos e consultas ao banco que não mudam a cada volta
Sair cedobreak ou return assim que achar o resultado
Evitar conversões e alocações desnecessáriasEm trechos executados milhares de vezes
Medir com StopwatchSempre, e em modo Release (Ctrl+F5)

6. Depuração

Depurar é encontrar e eliminar a causa de um defeito. Tipos de erro:

TipoQuando apareceExemplo
SintaxeAo compilarFaltou ;
ExecuçãoCom o programa rodandoDivisão por zero, referência nula
LógicaO programa roda, mas o resultado está errado> no lugar de >=

Método de depuração

  1. Reproduzir o defeito de forma confiável (um teste é o ideal).
  2. Isolar: em que ponto o valor deixa de ser o esperado?
  3. Formular uma hipótese sobre a causa.
  4. Verificar com o depurador (não adivinhe).
  5. Corrigir uma coisa por vez.
  6. Confirmar rodando os testes e conferir se nada mais quebrou.

7. Rastreabilidade

É a capacidade de seguir o caminho entre o requisito, o código que o implementa, o teste que o verifica e o commit que o registrou. Serve para saber por que o código existe e o que pode quebrar ao mudá-lo.

FerramentaPara quêComo
Ir para a definiçãoVer onde um método foi criadoF12
Localizar todas as referênciasVer onde algo é usado (impacto de uma mudança)Shift+F12
Hierarquia de chamadasVer quem chama o métodoCtrl+K, Ctrl+T
Ir para tudoAchar classe, método ou arquivo pelo nomeCtrl+T
Histórico do GitVer quem mudou o quê e quandoGit → Exibir Histórico / git log
Anotação (blame)Ver o autor de cada linhaClique direito no código → Git → Anotar / git blame

Boas práticas de commit

  • Commits pequenos: uma mudança lógica por vez.
  • Mensagem que cita o requisito: RF03: permite sacar até saldo + limite.
  • Nomes de teste que citam o requisito ou o cenário.

8. Testes unitários

Teste unitário é um pequeno programa que verifica automaticamente uma unidade de código (um método ou classe) isolada. Rodá-los a cada mudança dá segurança para evoluir.

Característica (FIRST)Significado
FastRápido: roda em milissegundos
IsolatedIndependente: um teste não depende do outro
RepeatableRepetível: mesmo resultado sempre
Self-validatingAutoverificável: passa ou falha, sem análise manual
TimelyOportuno: escrito junto com o código

Padrão AAA

  • Arrange (preparar): criar objetos e dados.
  • Act (agir): executar o que está sendo testado.
  • Assert (verificar): comparar com o resultado esperado.
Recurso do xUnitFunção
[Fact]Teste simples, sem parâmetros
[Theory] + [InlineData(...)]Mesmo teste com vários conjuntos de dados
Assert.Equal(esperado, atual)Verifica igualdade
Assert.True / FalseVerifica condição
Assert.Throws<T>(() => ...)Verifica se a exceção esperada é lançada
Assert.Null / NotNullVerifica nulos
Assert.Contains / EmptyVerifica coleções

Nome do teste: Metodo_Cenario_ResultadoEsperado, por exemplo Sacar_AcimaDoDisponivel_LancaExcecao. Ao falhar, o nome já diz o que quebrou.

TDD (desenvolvimento guiado por testes)

Importante: TDD é uma estratégia de desenvolvimento útil em muitos contextos, mas não é a única forma profissional de produzir software. Nesta UC, use-o para experimentar o ciclo teste → implementação → refatoração e comparar com seu fluxo habitual.
  1. Red: escreva um teste que falha.
  2. Green: escreva o mínimo de código para passar.
  3. Refactor: melhore o código mantendo os testes verdes.

9. Identificando erros conforme o requisito

Um defeito é a diferença entre o comportamento esperado (requisito) e o comportamento real. Para isso o requisito precisa ser claro, específico e testável.

Requisito ruimRequisito bom (testável)
“O saque deve funcionar direito.”“RF03: o saque só é permitido se o valor for maior que zero e menor ou igual ao saldo mais o limite.”
“O sistema deve ser rápido.”“A consulta ao extrato deve responder em até 2 segundos com 10.000 movimentações.”

Ao encontrar um erro, classifique: defeito de código (não cumpre o requisito), requisito ambíguo (precisa de esclarecimento) ou requisito faltando (nunca foi pedido). Registre sempre com: o que esperava, o que aconteceu e como reproduzir.
