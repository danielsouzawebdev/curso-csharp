Prática guiada · Melhorando a qualidade do projeto de estoque

🧭 Como executar esta práticaDigite o código, execute a cada etapa e compare o comportamento com o resultado descrito. Se houver erro, leia a mensagem antes de alterar o código e use o depurador quando indicado.

Cenário: sua turma desenvolveu um sistema de controle de estoque em Windows Forms. Durante as 4 primeiras semanas (sprint 1), os testes e usuários registraram 30 defeitos. Você é o time responsável por reduzir esses defeitos nas próximas semanas, aplicando a gestão da qualidade com dados e não com palpites. Se desejar, use os defeitos reais do seu próprio projeto no lugar dos registros fornecidos.

Automatize a análise com C#

Criar o Pareto à mão é bom para aprender, mas em um projeto real os dados mudam toda semana. Crie um Aplicativo de Console e substitua o Program.cs. Confira se a saída bate com o seu cálculo.

// Program.cs (Aplicativo de Console, .NET 6 ou superior)

// Códigos dos tipos de defeito, na ordem dos registros D01 a D30:
// V = Validação de entrada, R = Regra de negócio, I = Interface, B = Banco de dados, C = Cálculo, O = Outros
string[] tipos =                                        // array de textos: um item para cada defeito
{
    "V","V","R","I","V","B","R","V",                    // semana 1 (D01 a D08)
    "V","R","I","V","C","V","R",                        // semana 2 (D09 a D15)
    "R","V","V","I","B","V","R","O","I",                // semana 3 (D16 a D24)
    "V","R","I","B","C","O"                             // semana 4 (D25 a D30)
};

// Dicionário: associa cada código ao nome completo, para exibir no relatório
var nomes = new Dictionary<string, string>
{
    ["V"] = "Validação de entrada",                     // ["chave"] = valor
    ["R"] = "Regra de negócio",
    ["I"] = "Interface e usabilidade",
    ["B"] = "Banco de dados",
    ["C"] = "Cálculo",
    ["O"] = "Outros"
};

var contagem = tipos                                    // parte do array com todos os defeitos
    .GroupBy(t => t)                                    // agrupa códigos iguais (todos os "V" juntos, etc.)
    .Select(g => new { Codigo = g.Key, Qtd = g.Count() }) // para cada grupo: o código e quantos itens tem
    .OrderByDescending(x => x.Qtd)                      // do tipo mais frequente para o menos frequente (ordem do Pareto)
    .ToList();                                          // transforma em lista para podermos percorrer

int total = contagem.Sum(x => x.Qtd);                   // soma todas as quantidades (deve dar 30)
double acumulado = 0;                                   // guarda o percentual acumulado, que vai crescendo

Console.WriteLine($"{"Tipo",-26}{"Qtd",4}{"%",8}{"Acum.",8}  Foco?"); // cabeçalho; ,-26 alinha à esquerda em 26 colunas
foreach (var item in contagem)                          // percorre os tipos já ordenados
{
    double percentual = 100.0 * item.Qtd / total;       // 100.0 (com ponto) força divisão com decimais, não inteira
    acumulado += percentual;                            // soma ao acumulado
    string foco = acumulado <= 80.0 ? "<< foco" : "";   // marca os tipos que, juntos, chegam a cerca de 80%
    Console.WriteLine($"{nomes[item.Codigo],-26}{item.Qtd,4}{percentual,7:F1}%{acumulado,7:F1}%  {foco}"); // F1 = 1 casa decimal
}

Investigue as causas com o Diagrama de Ishikawa

Problema: “Defeitos de validação de entrada chegando aos usuários”. Em equipe, faça um brainstorming e distribua as causas nas categorias abaixo. Exemplos de ponto de partida (complete com mais causas):

Método
Não há padrão de validação; revisão de código não existe
Ferramentas
Controles livres (TextBox) em vez de máscara ou ComboBox
Requisitos
Regras de formato não descritas nos requisitos
Pessoas
Pressa; falta de treinamento em validação
Medição
Sem testes para entradas inválidas
Ambiente
Prazo curto; ausência de testadores

Chegue à causa raiz com os 5 Porquês

Escolha a causa mais provável do Ishikawa e pergunte “por quê?” até chegar a algo que a equipe consiga mudar. Exemplo:

  1. Por que o campo e-mail aceitou texto sem @? Porque ninguém validou o formato.
  2. Por que ninguém validou? Porque o requisito não pedia.
  3. Por que não pedia? Porque os requisitos não têm uma seção de regras de entrada.
  4. Por que não tem? Porque o modelo de requisitos da equipe não prevê isso.
  5. Por que não prevê? Porque o modelo nunca foi revisado com base nos defeitos.

Causa raiz: o modelo de requisitos e o processo de revisão não tratam validação de entrada. Faça o mesmo para a causa do segundo tipo mais frequente (regra de negócio).

Execute o ciclo PDCA e acompanhe com a carta de controle

Registre o ciclo:

EtapaRegistro

DoAs ações do 5W2H começam na semana 5

Os defeitos das semanas 1 a 10 foram: 8, 7, 9, 6, 8, 7, 17, 6, 5, 6. Calcule a média, o limite superior (média + 3√média) e o limite inferior (média − 3√média, com mínimo 0). Há algum ponto fora dos limites? Use o programa abaixo para conferir.

// Acrescente ao Program.cs (ou crie outro projeto) para a carta de controle.

int[] semanas = { 8, 7, 9, 6, 8, 7, 17, 6, 5, 6 };      // defeitos registrados nas semanas 1 a 10

double media = semanas.Average();                       // Average() calcula a média aritmética do array
double desvio = Math.Sqrt(media);                       // em contagem de defeitos (carta c), o desvio padrão estimado é a raiz da média
double lsc = media + 3 * desvio;                        // Limite Superior de Controle = média + 3 desvios
double lic = Math.Max(0, media - 3 * desvio);           // Limite Inferior: Math.Max garante que não fique negativo (defeito não é negativo)

Console.WriteLine($"Média = {media:F2} | LSC = {lsc:F2} | LIC = {lic:F2}"); // mostra os limites com 2 casas decimais

for (int i = 0; i < semanas.Length; i++)                // percorre cada semana pelo índice
{
    bool fora = semanas[i] > lsc || semanas[i] < lic;   // || significa "ou": fora se passou de qualquer limite
    string situacao = fora ? "FORA DE CONTROLE: investigar!" : "dentro dos limites"; // texto conforme o caso
    Console.WriteLine($"Semana {i + 1,2}: {semanas[i],3} defeitos  {situacao}");     // i + 1 porque o índice começa em 0
}

Interprete a carta de controle

Ver o resultado e a interpretação

Interpretação: a média é 7,9, o limite superior é 16,3 e o inferior é 0. A semana 7 está fora de controle: não é variação normal, mas uma causa especial. Pergunte: o que aconteceu naquela semana? (Exemplo: entrega com prazo apertado, revisão pulada.) Depois da investigação, registre a causa e a ação para evitar a repetição. As semanas 8 a 10 ficaram todas abaixo da média, um sinal de que as ações do plano podem estar funcionando, mas isso deve ser confirmado com mais semanas de dados antes de padronizar.

Faça uma revisão por pares e registre

Troque o código com outra dupla e use o checklist de revisão da Avaliação. Registre em ata: data, participantes, itens verificados, defeitos encontrados e responsável por cada correção. Cada defeito encontrado entra no registro com ID único (D31, D32...) para alimentar os próximos Paretos.

Faça a retrospectiva e reinicie o ciclo

Com a equipe, responda em 20 minutos e registre em ata:

O que foi bem?O que pode melhorar?Quais ações vamos tomar?

Cada ação deve ter responsável e prazo. Elas entram no Plan do próximo ciclo PDCA, e o ciclo continua. Isso é a melhoria contínua.
